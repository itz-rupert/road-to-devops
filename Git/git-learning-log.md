GIT LEARNING

- Version control is all about having copies of an edited file and you are able to keep track of all the changes and modifications overtime also knowing who made the changes, when and also you can go back to a particular file version, edit that same file and also have different variations of that same file.
- In the open source world where contributions are made all over the world version control is very important cause you need to track who is making what contribution, why they are making the contributions and they can merge all together or they can make a branch of a particular file version and maintain that branch.
- Using the command "git init" turns a folder where you keep your work into a repository and from there can now track the changes made to that directory.
- A "branch" is like an independent copy of your work.
- "Tagging" is to mark a specific point in time on a branch. For example you can tag at a point version one and version two and then someone who needs version one will go to the tag and download it and it is all in the same repository. You can "checkout" of a branch to make changes for example checking out of version two and making changes in version one but then version two is still the same way you left it.
- "Commit" add changes you have made to the repo, while push is when you send changes to a remote repository. The directory where you store your repository on your computer is called your workspace.
- Untracked changes are new files that git has not been told to keep track of yet (not git add yet to your staging area).
- Working area is where you are doing your modifications to files but you have not committed them yet.
- Staging area is where you have files that have been modified but these files are marked for the next commit and once you commit your files they go into the local repository.
- The remote (upstream) repo is the online location where files are stored (hosted repo on a shared server) like GitLab or GitHub.
-Most applications these days are hosted on internal git servers, so this is one of the reasons to study git.

## BASIC GIT WORKFLOW
- git is not the same as Github, because git is a software that runs on your computer while GitHub is  an online service where git repos can be hosted.
- So when you run "git commit" you are running git locally and when you do something like "git push" you are sending your local commits to a remote repo such as GitHub. Now imagine you are working with someone on the same project and they push the changes to GitHub you can take those changes to your local repo with "git pull". (LOCAL → REMOTE with push and REMOTE → LOCAL with pull). 
- So for example you can have a folder and then run "git init" to turn it into a git repo, then git creates a hidden directory called ".git". It basically says start tracking this directory with git.
- Now when you run "git status" you are asking git to tell you what is happening in your repository.
- Now suppose you create a new file (notes.txt) and then you run git status, it will show you that you have untracked files. You have to run "git add notes.txt or git add ." to take those changes you have made to the staging area where your changes can now go to GitHub.
- You can now SAVE (create a commit with a description) by running the command "git commit -m "new file made"
-run git remote -v to see your remote repos and you can find a project on GitHub and want a copy on your computer all you have to do is run "git clone <repo URL>" so git will download the repo including its git history. run git remote add origin <repo URL> to add a remote repo and then your first push is usually "git push -u origin main"
- use git diff to see changes that have been made but have not been staged yet.
- use "git rm old-file.txt" when you want to remove a file and let git know about it and then you can commit the changes using "git commit -m "Remove old file".
-git branch allows you to work on different versions/lines of development. You can add a branch with git branch python, check on branches with git branch and then switch to the branch with git switch python or doing it all in one go that's is "git switch -c python" (create and switching in one command).
-use git restore when you make a change and want to discard it but you have to be careful. Basically this means that you should delete the current uncommitted changes (NO GIT ADD yet ) to the file I am working on and then take it back to the previous committed version (the version that has been git added).
- So now imagine you have a repo in GitHub that is not on your laptop you can run git clone to get that repo, its history and all into your laptop but then when new commits are made to that repo you use git fetch (basically saying go and check what is new and then it downloads the new commit information without changing the file you are working on automatically.
- git diff shows you changes you have made that have not been stages yet. With git pull you are able to retrieve changes that have been made in the remote repo and have them integrated into your current branch (different from git fetch which does not change file you are working on).

-A pipeline file is a script that tells a system to automatically tun a series of streps whenever something happens in your repo (a push, a PR, a schedule, etc). The most common ones I will encounter are in the order of tool and file location: GitHub actions - GitHub/workflows/something.yml, GitLab CI-gitlab-ci.yml, CircleCI - circleci/config.yml, Jenkins -Jenkinsfile.
-In Git, I can create a feature branch using git switch -c add-login-page, make changes, save them with git add . and git commit, then upload the branch to GitHub using git push -u origin add-login-page. I can open a pull request on GitHub to have the changes reviewed and merged into main. Once merged on GitHub, I update my local main using git switch main and git pull origin main. git clone copies a remote repository to my machine, git fetch downloads remote updates without merging them, git pull fetches and integrates changes from a remote branch, git push uploads commits, and git merge combines one branch's changes into the branch I'm currently on. If I want to merge locally, I switch to main and run git fetch origin followed by git merge origin/add-login-page; I can then push the merge to GitHub if I have permission. Merging does not automatically delete a feature branch, and pulling main does not merge an unmerged feature branch into it.
